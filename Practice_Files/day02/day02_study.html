Day 2: mutexes, races & deadlocks

A peer-style walkthrough for the files in this folder. The goal is not just to make the code run—you should be able to explain what every thread is waiting for.

42 peer tip:

Before touching the mutex API, remember the real problem: threads share process memory. If two threads update the same variable at the same time, the result depends on timing.

shared data→critical section→protect with a mutex
Race
Two threads access shared state without coordination.
Mutex
One thread enters the critical section at a time.
Deadlock
Threads wait forever for locks held by one another.

1. The race: watch the lost update

In 01_race.c, each worker does this:

local = g_counter;  /* read */
local = local + 1;  /* modify */
g_counter = local;  /* write */

If every worker reads 0 before any worker writes, all five calculate 1. Five increments happened, but the final write can still be 1.

Start the simulation.

2. The mutex: protect the critical section

In 02_mutex.c, the lock surrounds the read/modify/write operation. A thread that cannot lock waits; it does not enter the critical section early.

pthread_mutex_lock(&g_counter_mutex);
g_counter = g_counter + 1;  /* critical section */
pthread_mutex_unlock(&g_counter_mutex);
No worker has tried the mutex yet.

3. The deadlock: draw the wait cycle

03_deadlock.c deliberately creates this situation. It is expected to hang, so do not run it without a timeout.

Thread A
owns lock1
waits for lock2
Thread B
owns lock2
waits for lock1
Both threads are ready.
timeout 3s ./03_deadlock

4. Fix: agree on one lock order

In 04_deadlock_fixed.c, both workers acquire lock1 before lock2. One may wait, but there is no circular wait.

pthread_mutex_lock(&g_lock1);
pthread_mutex_lock(&g_lock2);
/* use both resources */
pthread_mutex_unlock(&g_lock2);
pthread_mutex_unlock(&g_lock1);

The rule to remember:

When several locks are needed, define a global order and always acquire them in that order.

  • Why can the race finish below 5?
  • Which lines are the critical section?
  • Why does pthread_join not fix a race by itself?
  • Which Coffman condition is removed by consistent lock ordering?
  • Why must a mutex be destroyed only after all users are finished?
Answer check:
Join waits until a thread finishes; it does not protect simultaneous accesses. A mutex protects the critical section. Consistent ordering removes circular wait.
